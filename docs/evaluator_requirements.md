# Evaluator / Programmer Requirements

*A specification a reviewer or collaborating programmer can judge this project against without asking the author anything. Every criterion below is measurable — "runs with one command," not "good code."*

## 1. Scope & objective

This project delivers a **reproducible comparative study of day-ahead hourly electricity-load forecasting** for Brazil's SE/CO subsystem, using open ONS data with calendar and temperature exogenous features. The deliverable is a repository — code, documentation, and saved results — in which a reviewer can (a) reproduce the headline result with a single command in about a minute, (b) verify that the evaluation is temporally honest and leakage-free, and (c) read a business-facing account of what the forecast improvement is worth in dispatch cost. **No model serving, API, or deployment is delivered**; the study ends at a validated, documented comparison.

## 2. Audience & assumptions

The primary reader is a **data-science recruiter or hiring technical lead**, reviewing in under ten minutes. Secondary readers: a technical reviewer verifying method, and a business stakeholder reading only the impact framing. Assumptions: the reviewer has Python 3.11+, no GPU, an internet connection for first-time dependency and data fetch, and **no prior context about the project or Brazilian electricity markets**. Everything needed must be in the repo.

## 3. Functional requirements

- **F1 — Verified ingest.** Raw data is fetched from documented public sources and checksum-verified before use. *Verify:* `python run_all.py --stage data` checks SHA-256 of every file in `data/raw/` and aborts on mismatch.
- **F2 — Documented cleaning.** Type coercion, gap handling and DST-transition flagging are explicit, with no silent imputation. *Verify:* `src/limpar.py` sanity checks abort on divergence from `reports/FACTS.md`.
- **F3 — Origin-safe features.** Calendar and lag features are all computable at the forecast origin. *Verify:* `src/gerar_features.py` leakage self-test reports 0 divergences.
- **F4 — Four models.** A baseline plus ≥2 alternatives plus the candidate (seasonal-naïve, SARIMA, Prophet, Chronos-2).
- **F5 — Identical evaluation.** Every model on the same held-out temporal split, day-ahead, sliding origin, over 2024-01-01+.
- **F6 — Persisted outputs.** Forecasts and a comparison table exist on disk: `data/processed/*_previsoes.parquet`, `reports/tabela_comparativa.csv`, charts in `reports/figures/`.
- **F7 — Single entry point.** `python run_all.py` runs end-to-end (~1 min); `--help` lists stages and their cost.
- **F8 — Controlled ablation.** The optional temperature layer is compared with context held identical between conditions.

## 4. Quality requirements (measurable)

**Time-series correctness (non-negotiable).** Q1 — **no shuffling**; the split is temporal, a random split anywhere is a fail. Q2 — **no leakage**; every feature and forecast is recomputable from data strictly before its origin, with automated tests reporting **0 divergences**. Q3 — **lags ≥ 24 h** for a day-ahead horizon. Q4 — **test touched once**; nothing selected by looking at test performance.

**Reproducibility.** Q5 — dependencies pinned to exact versions. Q6 — seeds fixed (`seed=42`) and single-threading documented where the optimizer is otherwise nondeterministic. Q7 — re-running reproduces headline metrics **exactly** (Chronos-2 MASE 0.4363, MAPE 1.8235%); drift is a fail signalling nondeterminism or a broken split. Q8 — relative paths only; no secrets or absolute local paths committed.

**Documentation.** Q9 — every number in prose traces to `reports/FACTS.md`, generated by code and idempotent. Q10 — limitations name concrete failure modes rather than hedging.

**Code style & tests.** Ruff is configured (`pyproject.toml`, `ruff check src/ run_all.py`, `docs/SETUP.md` §9). No unit-test suite — a deliberate scope choice, not an oversight: the real correctness risks in this project are **data integrity and temporal leakage**, not isolated function behavior, and both are already covered by gates that abort the pipeline on failure (MANIFEST hash verification, `verificar_facts.py`'s independent recomputation, the leakage self-tests in `gerar_features.py`/each model script, and the FACTS.md-divergence checks in `run_all.py --stage results`). A conventional unit-test suite would check function-level behavior these gates don't target, at the cost of maintaining tests separate from the pipeline that already has to run correctly for the project's headline claim to hold.

## 7. Out of scope

No serving, API, container, or scheduled job. No real-time inference, monitoring, or drift detection. No merit-order dispatch modelling (the cost metric is an explicitly declared proxy). No forecasting horizon beyond day-ahead. No subsystems other than SE/CO as the primary case (others are robustness checks only). Deployment is deliberately deferred to a separate project.

## 8. Reviewer notes — where to start

Start at `README.md` (30 s), then `references/one_pager.md` if you want the business case only. To verify method, run `python run_all.py` and confirm it reproduces the headline metrics, then read §4 (methodology) and §7 (limitations) of `docs/technical_report.md`. **Focus your scepticism on two things:** whether the temporal split is genuinely leakage-free (see the self-tests), and whether the cost metric's assumption is stated rather than hidden — the project's strongest claim depends on both.
